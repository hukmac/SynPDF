SynPDF
======

[__Synopse PDF engine 1.18 extended__](SynPdf.pas) with:
- basic implementation of ExtGSate,
- alpha blending control through TPdfDocumentGDI/TPdfCanvas (PDF level commands),
- alpha blending and GSave/GRestore control through EMF (GDI level commands).

Sample Code:
-------
Example demo project showcasing alpha blending in PDF documents using both mechanisms is in [__examples__](examples/) directory. PDFs generated by it are in [__documents__](documents/). One of the examples ([alpha_blending_with_GDI_and_MetaExtChannel.pdf](/documents/alpha_blending_with_GDI_and_MetaExtChannel.pdf)):

The demo program generates two simple PDF files:

  1. First, using direct TPdfCanvas commands (PDF stream-level drawing),
  2. Second, using standard GDI drawing via TMetafileCanvas and TMetaExtChannel (EMF level embedding).

To generate pages of the second file, one can use procedures:
   - DrawToMetafile() : standard case, 'identical' as in first file, and
   - DrawToMetafile_ProblematicMixingWithGSaveGRestore()
>[!TIP]
>The second procedure allows to visualize some problems one can face when mixing PDF level and GDI level commands. A detailed description of these problems is at the end of [this example file ](/examples/UMainFrm.pas) (below the code).

Programming Interface:
--------
The proposed interface exposed in [__SynPdf.pas__](SynPdf.pas) is constructed with stress put on the simplicity of its use.

To send PDF commands through EMF/TMetafileCanvas one can use a set of provided wrappers of TMetaExtChannel methods:
```
procedure SetAlphaBlendMode(canvas :TCanvas; stroke_alpha, fill_alpha :Single; blend_mode :TPdfBlendMode); {alpha: reals from 0-1 as in PDF}
procedure SetAlphaBlend(canvas :TCanvas; stroke_alpha, fill_alpha :Byte; blend_mode :TPdfBlendMode);       {alpha: integers from 0-100 as in GDI+}
procedure GSave(canvas :TCanvas);
procedure GRestore(canvas :TCanvas);
```

To send PDF commands through TPdfDocumentGDI canvas one can use methods of TPdfCanvas:
```
procedure TPdfCanvas.SetAlphaBlendMode(aAlpha_stroke, aAlpha_fill :Single; aBlend_mode :TPdfBlendMode);    {alpha: reals from 0-1 as in PDF}
procedure TPdfCanvas.GSave/GRestore; (implemented in earlier versions of SynPdf engine)
```

Implementation Details:
-------

### **Alpha blending control through EMF**

Alpha blending control through EMF is realised with help of TMetaExtChannel class. 

> [!NOTE]
> TMetaExtChannel provides a simple mechanism to encode PDF commands (like alpha blending and save/restore operations) into a metafile stream by using special "signal" shapes based on polylines. These signal shapes, when identified during EMF parsing, are eliminated from drawing to avoid affecting the visual output. In the SynPdf engine, this is done at the beginning of EnumEMFFunc(). As a result, TMetaExtChannel signals form a transparent, one-directional channel to transport messages with PDF commands.

Main pros of this solution are:
- overcomes limitations of EMF standard without any modifications of it,
- can be easily plugged in to the SynPdf engine,
- is very simple and can be further extended.

In the proposed implementation it can be also fully disabled by definition of NO_USE_META_EXT_CHANNEL compile switch.

### **TMetaExtChannel signals**

A TMetaExtChannel signal includes two parts: header and data. Both header and data are lists of TPoint and together form a signal polyline. To limit the probability of conflict with the canvas content, the header part can be one of two hopefully unique shapes:
 - a polyline forming letters of the word 'SIGNAL' placed one over another (default), or
 - a polyline forming a "zero-size" rectangle (0,0,0,0), which is faster but less safe.
   
For the same reason, it can be requested that a signal must be sent/received multiple times to form a single message. Thus there are four types of messages defined: **mtSingleRect**, **mtMultiRect**, **mtSinglePoly**, **mtMultiPoly** (default is mtMultiPoly == 5 signals). In the current version of TMetaExtChannel, each repetition of the signal includes the same data. But there is no limitation to extend amount of transferred data when needed - both by increasing the size of signal data segment as well as by splitting data between many signals.

### **TPdfExtGState lists**

TPdfExtGState class type is used to form a TPdfDocument's global list of unique ExtGState PDF settings (alpha, blending mode), with references to their definitions in the PDF xref (IDs kept in ObjectNumber). These objects are added to page-related lists (TPdfCanvas.FPageExtGStateList) when related ExtGStates are used on a given PDF page. This is why /ExtGState dictionary is created and added to /Resources dictionary od a page not in TPdfDocument.AddPage (as Fonts or XObjects) but in TPdfCanvas.RegisterExtGState.

>[!CAUTION]
>TPdfExtGState objects are including only the information about alpha stroke&fill and blending mode (CA, ca, BM). Other elements such as font selection, line width (LW), line cap (LC), dash pattern (D), or mitter limit (ML) are not included in the current implementation of ExtGState. This is for further development.

### **ExtGState Timings**

Proposed SetAlphaBlend() wrapper is quite fast: 2.1 – 10.2 µs/call, depending on configuration of TMetaExtChannel. This is negligible in comparison to the time of rendering of the EMF with a large number of distinct ExtGStates - as it is done with TPdfCanvas.RenderMetaFile (function EnumEnhMetaFile in GDI32). Because the latter can take considerable amount of time, below a simple comparison is presented.

Approximate EMF rendering and ExtGStates creation timings as a function of the number of ExtGStates (gathered with i9-9900K 3.2 GHz) for PDF with one empty page and many distinct ExtGStates:
      
| # of ExtGStates  |  Rendering time  | Adding ExtGStates |
|------------------|------------------|-------------------|
|  1.6k            |  137 ms          |   16ms  (11.7%)   | 
|  16k             |  3.1 s           |   163ms (5.26%)   | 
|  32k             |  14.2 s          |   326ms (2.29%)   | 
|  64k             |  100 s           |   653ms (0.65%)   | 
|  128k            |  504 s           |   1.3s  (0.25%)   | 
      
Happily, the expected number of distinct ExtGStates in a typical PDF is below 1000, and in a large, complex PDFs is often below 10k. Adding of ExtGStates was measured with mtMultiPoly setting of TMetaEstChannel. Time cost of adding ExtGStates with mtSinglePoly would be almost five times shorter.
